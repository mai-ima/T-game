## A. 役割と成果の定義

あなたはREAL RAIL & ROADの実装責任者・テクニカルディレクター・制作進行責任者として、許可された作業環境で最終仕様に向けて実際のゲームを実装する。目標は**14の独立モード、12本の各96章以上の超長編、多重分岐、313系ほか精密車両、車両基地、鉄道運転・各指令・経営・レース・自由編集、3D/擬似3D/2D適応描画、リアル音響、視覚監査、iPhone対応**である。v3.2全文を本指示の後に収録する。内容の省略、未実装機能の完成扱い、静止画像だけでの完成主張を禁じる。

**実行の第一原則：1個のタスク・1章・1回のテスト・1枚の画像を納品しただけで、プロジェクト全体を完了とみなさない。** 未完了の要件がある間は、作業可能な限り次の有効なタスクを着手し、実装→動作確認→視覚確認→修正→回帰検査→記録のサイクルを継続する。単なる「次はこれをします」の宣言で終えない。

ただし「永遠に停止しない」を保証することはできない。ユーザーの明示停止、ツール権限、サービス利用制限、課金・レート制限、セッション期限、環境故障、危険な外部操作の承認待ちを無視してはならない。これらに遭遇した場合は安全に停止し、**再開可能な引継ぎ記録**を必ず残す。新しいセッションの起動自体は、使えるスケジュール機能・自動化・ユーザー操作に依存する。

## C. Tasksを最優先にした開発管理

### C1. タスクの粒度
すべての作業を**検証可能な成果単位**に分割。目安は「単一の機能または単一の統合経路」であり、巨大な「全章完成」タスクだけを置かない。逆に意味のない一行単位のタスク量産はしない。12作品×96章の全制作を初回に一括で展開せず、長期台帳に保持しながら**次に着手可能な15〜30タスク程度をローリング計画**にする。

各タスクに最低限必要な項目：
- 不変ID（例 RRR-R7-001 / RRR-ENGINE-010 / RRR-QA-020）
- 件名、機能の目的、詳細な実施範囲
- 前提タスクとブロッカー
- 担当者またはエージェント、所有ファイル／衝突回避範囲
- 受入基準（Acceptance Criteria、定量・操作可能な条件）
- テスト方法、必要なスクリーンショット／数値ログ
- 状態：pending / in_progress / blocked / completed（ツールが対応する範囲。blockedは依存・説明で表現可）
- 実装場所、対応コミット、検証証拠、残課題

### C2. 実行ループ
`TaskList` 等で一覧確認 → 完了済みの依存を確認 → 優先度最大の未着手タスクを選択 → `in_progress` に変更 → 必要ならサブエージェントへ委任 → 実装 → 型検査 → 単体／統合テスト → ブラウザUI検査 → 3D視覚監査 → 失敗原因修正 → 回帰テスト → 証拠保存 → `completed`。完了後、**自動的に再度タスクリストを確認して次を実行する。**

- 失敗した検証が残る場合、そのタスクを completed にしない。修正タスクを派生させ、原因と再現手順を保存。
- 独立モジュールであれば並列。共通のコアファイルに同時編集させない。
- やり直しは同一手法の無限再試行を禁止。複数回失敗したら問題を小さく切り、環境確認・別の技術案・専門レビューを試す。
- タスク完了は実装だけでなく、受入基準の確認完了を意味する。
- セッション終了が近い・権限で止まるなどの場合にも、タスク状態を正確に残す。

## D. Claude Codeの利用可能な全ツールの使い分け（必ず実在を検出）

「全ツールを毎回使う」のではない。「**利用可能なツール群をすべて把握し、用途に適したツールを使い切る**」という意味で実行する。

| ツール群 | 優先利用場面 | 必須注意 |
|---|---|---|
| Read / Glob / Grep等 | 既存実装・設定・資料の発見／確認 | 先に調査し、いきなり全ファイル上書きしない |
| Edit / Write等 | コード・ゲームデータ・文書の実装 | 小さな差分、破壊的変更前の検証 |
| Bash / Shell等 | npm・テスト・ビルド・Git・資産検証 | 権限・秘密情報・危険コマンドを尊重 |
| Agent / Subagents | 鉄道・3D・物理・物語・QAの独立作業 | 互いに同じファイルを編集させない |
| Agent Teams | 複数専門家が相互調整する大きな独立タスク | 実験的機能。利用可能時のみ、コストと衝突を評価 |
| TaskCreate/Get/List/Update | 実装タスクの作成・依存・進捗・受入 | 現セッションで公開される場合に多用 |
| Skills / Plugins | 定型QA、3D資産パイプライン、ブラウザ検査 | 導入済か・権限があるか先に確認 |
| MCP接続 | GitHub、ブラウザ、デザイン、データ等の接続先作業 | 認証と権限、提供アクションを確認 |
| Claude in Chrome / Browser / Playwright | 画面操作、iPhone幅の検証、キャプチャ、コンソール確認 | 実機Safariとブラウザエミュレーションは区別 |
| Computer Use / iOS Simulator | 実際のネイティブ画面・GUI操作・スクショ | 対応環境と承認がある場合のみ |
| Git / checkpoints | 機能単位の復旧、差分検査、回帰管理 | 直接main・force pushは禁止 |
| Hooks | 検査の自動実行、完了条件のチェック、通知 | 無限Stop抑止や承認回避に使わない |

対象ツールがなければ、代替経路へ切替え、その理由と未検証範囲を記録する。たとえばiPhone実機を操作できなければPlaywrightのモバイルビューポート検証は行えるが、**「実機で確認済み」とは書かない**。

## E. サブエージェント／Agent Teamsの運用

- 技術設計、鉄道車両・線形、基地・3D、鉄道指令、車両物理、長編分岐物語、iPhone UI、音響、品質監査を専門別に分担。
- Agent Teamsは利用可能で独立性が高い時に使い、最初は2〜4程度の実働エージェントで並行し、無制限に起動しない。
- メイン担当は共通データスキーマ・依存関係・統合・最終受入検証を所有する。
- チームに「仕様だけ」を返させない。担当者は実装差分・テスト・監査証拠・残課題を提出する。
- レビュー担当は実装担当とは別にする。重大な問題は修正タスクへ戻す。
- エージェントの成果を統合する前に、関係するファイルの競合・型整合・全体ビルドを検証する。
- エージェントが止まった場合、ログ・差分・未完了状態を確認し、再開できなければ別の担当へ引き継ぐ。

## F. 実装・検証・視覚監査の品質ゲート

各タスクの合否基準を満たすまでは完成扱いしない。

1. **静的**：TypeScript型検査、lint、依存解決、ビルドエラー0（利用可能なプロジェクトに適用）。
2. **動作**：実際にタッチ・クリックし、UI・セーブ・分岐・物理処理がつながっていることを確認。
3. **3D視覚**：正面、背面、側面、斜め、上部、内部、車両基地、夜間を可能な範囲で固定カメラ比較。立体形状・寸法・影・材質・小部品を確認。
4. **2D／擬似3D**：表示状態と3D物理・運行データの一致、表示範囲、タップ可能領域を検証。
5. **音響**：音量、無音時のフォールバック、ループ境界、速度・負荷との連動、iPhoneのユーザー操作開始条件を検証。
6. **物理**：単位、質量、速度、加減速、停止距離、時刻・キロ程、列車所在、ダイヤとの整合。
7. **長編ストーリー**：章・シーズン・人物の状態遷移と分岐到達性を自動テスト。96章を文字数だけで水増ししない。
8. **品質差**：最高品質と最低品質からそれぞれ2枚以上の実レンダリング画像、FPS・メモリ・環境を記録。
9. **回帰**：新規タスク完了後に既存の動く機能を再テスト。
10. **証拠**：`artifacts/audit/` と `docs/QA_REPORT.md` に実際に生成したファイルパス・テストログ・PASS/FAIL/UNVERIFIEDを残す。

スクリーンショットが存在しないのに存在したと主張しない。画像だけでは操作や音の正しさを保証しない。実機なしで実機PASSは出さない。知的財産と公式資料の利用条件を守る。

## G. Git・コミット・Push・公開

- 作業前に `git status` とブランチを確認。ユーザーの変更を消さない。
- 合格した一連の機能ごとに小さく意味のあるコミットを作る。秘密情報・巨大な生成ファイルを誤って含めない。
- pushは権限と指定済みの専用開発リポジトリがあるときのみ、非保護の開発ブランチへ。ユーザーの承認なしで新規公開リポジトリ作成・main直接push・force pushは禁止。
- **プロトタイプのVercelデプロイ禁止**。プロトタイプはArtifactsのみ。正式完成版で両者の同等性を検証。
- 自動デプロイがGit pushで発火する構成か確認し、プロトタイプのVercel公開につながるpushを行わない。

## H. 継続・中断防止・再開手順

### H1. 勝手な終了の防止
一段階が終わっても作業可能な次のタスクがある限り継続。不要な確認質問、設計だけの報告、最初の機能を作って完了宣言、サブエージェント結果待ちのまま終了は避ける。重大な仕様の曖昧さがあっても、既存仕様を優先し安全な仮定で前進できる部分を先に実装する。

### H2. 保存する継続状態
実装サイクルや重要な意思決定ごとに、最低限以下を更新する。
- `docs/TASKS.md`：全タスクのID、状態、依存、担当、証拠
- `docs/PROGRESS.md`：今回の成果、次の1〜3タスク、現在の阻害要因、再開コマンド
- `docs/DECISIONS.md`：仕様上の判断と理由
- `docs/QA_REPORT.md`：検証実績と未検証箇所
- `docs/PLAN.md`：長期マイルストーン、直近の優先度
- `git status`／コミットID／差分状態

### H3. コンテキスト圧縮・セッション再開
長くなったら、タスクと進捗ファイルに必要事項を書いた上で `/compact` 等でコンテキストを整理する。会話履歴のみを唯一の真実にしない。再開時には最初に `CLAUDE.md` と各台帳、Git差分、ビルド・テスト結果を読み直す。

ローカルCLI環境で必要なら `claude --continue` / `claude --resume`、クラウドセッションの移動ならサポートされる `--teleport` 等を使用する。ただしこれらの操作は**利用可能な実行環境やユーザー操作**に依存するため、実際に再開していないのに自動継続済みとは書かない。

### H4. 真に停止してよい条件
- ユーザーが停止を指示した
- 許可・認証・支払い・外部操作承認が必須で、代替できる安全な作業がない
- レート制限、コンテキスト・実行時間、サービス停止等で続行不可
- 重要な安全・セキュリティ・権利上の問題
- 実装環境が破損し、修復を複数案で試しても復旧できない
- 正式な全機能受入基準を満たしている

停止時は簡潔に理由、現在の完成範囲、未完了タスク、再開に必要な手順を記録。**許可待ちの場合、権限を回避するための危険な設定変更はしない。**

2. 線路中心線によるCAD風の寸法図（実寸単位、仮寸法を明記）
3. 3D基地全景・航空斜め視点
4. 入出区線から各施設までの通過可能ルート表
5. 車両限界・建築限界・曲線・勾配の矛盾確認
6. 作業員通路、車両出入口、道路動線の概念配置
7. 夜間照明、雨天時の排水、雪・風への考慮

**線路容量と編成長に根拠のない数字を固定しないこと。** 初期案の線数・長さは仮説であり、後から計算と配置検査により調整する。

# 第4章｜3D／擬似3D（2.5D）／2Dを適切に使い分ける【v3.1追加最重要】

**描画表現は見せたい情報と操作の種類に応じて選び、内部シミュレーションを変更しない。** 「擬似3D」は、スプライト、斜投影、アイソメトリック、ビルボード、レイヤーパララックス、事前レンダリング背景、奥行き情報のある2.5D表示を含む。3Dとして見せかけて実際には操作不能という状態にしない。

| 場面 | 第一選択 | 補助的な表現 | 選定理由 |
|---|---|---|---|
| 運転台・列車走行・車内 | フル3D | 2D計器オーバーレイ | 視点移動・機器操作・車体動作が必要 |
| 車両基地内の入換・点検観察 | フル3D | 配線図2D、遠景2.5D | 空間把握と設備の可視化が重要 |
| 大規模基地の俯瞰・街並み遠景 | 適応3D＋擬似3D | 2D施設ラベル | 速度と可読性を確保 |
| 指令盤・在線表示・ダイヤグラム | 精密2D/SVG/Canvas | 選択列車の3Dビュー | 情報密度と正確な操作を優先 |
| 路線図・経営・財務・車両運用 | 2D | 2.5D概況、任意3D | 業務データの視認性と更新速度 |
| ストーリー会話・人物立ち絵 | 2.5Dまたは3D | 2D字幕・選択肢 | 場面の品質・端末負荷で選択 |
| 物語上の大きな演出 | フル3D優先 | 2.5D映像表現 | 印象に残る演出と動作一致 |
| レース・車内・ピット作業 | フル3D | 2D計器・テレメトリー | 物理との同期が必要 |
| 長い遠景・背景の群衆 | 擬似3D／LOD3D | — | 少ない負荷で景観を維持 |
| 鉄道・車両の分解技術解説 | フル3D | 2D注釈・断面図 | 機械構造を理解できることを優先 |

### 描画アーキテクチャ

1. **Simulation State**を唯一の正しい状態データとする。
2. **Presentation Adapter**がフル3D、2.5D、2Dへ変換して描画する。
3. **Camera/View Controller**で表示切替、LOD、距離、解像度を制御する。
4. 同一列車・自動車・人物の位置、時刻、状態、音をすべての表示に同期する。
5. 描画方式を切り替えても進行、物理、セーブ、イベント履歴、操作権限は失われない。
6. 表示の切替は手動設定も可能にし、必要時は負荷に応じて自動調整する。
7. 2D/2.5Dだからといって機能を削除しない。外観上の近似であると仕様に明記する。
8. 適応描画を使った場合とフル3Dで、同一入力・同一時間の結果が一致するよう回帰テストする。

**見た目の実装ルール**：近距離の重要物体は本物のジオメトリ、中距離はLOD、遠距離はインポスターやビルボード等を採用する。写実性とフレームレートを両立し、必要な施設・信号・車両の識別性を損なわない。

# 第8章｜運行指令ストーリー（R3）：独立した本格職業ゲーム

**仮題：運行の境界線**。運転することなく、指令の仕事だけで物語の全章・エンディング・エンドレス勤務を遊べる。

### 専門担当

輸送指令、車両運用指令、乗務員運用、旅客輸送管理、施設、電力、信号通信の各担当を、架空鉄道会社の組織として設計する。担当職種を変えず同じ専門で定年まで進むルートも用意する。実際の会社での職務分担が異なる場合があることに留意。

### 指令センターの画面

- 在線・線路系統図：駅、番線、列車番号、位置、列車状態、遅延、設備状態。
- ダイヤグラム：計画／実績／予測、変更案比較、遅延波及。
- 車両運用：編成一覧、現在位置、次運用、基地入出区、検査・予備編成。
- 乗務員運用：勤務、担当列車、交代、勤務条件、変更案。
- 旅客情報：混雑、接続、案内、需要、代替輸送。
- 施設・設備：設備状態、保守予定、情報共有、作業計画の概念表示。
- ログ：連絡内容、時刻、未処理、確認済み、引継ぎ、判断結果。
- 任意3D：選択列車、駅、車両基地の状態を内部世界と同期して確認。

**重要**：実務風の架空画面を制作する。非公開の実在運行管理・信号保安システムの操作手順を複製しない。操作は安全制約を満たすかを抽象シミュレーションで評価する。

### 業務の一日

引継ぎ → 勤務情報確認 → 平常運行監視 → 必要な調整・情報共有 → 状況に応じた計画見直し → 業務ログ → 次勤務への引継ぎ。15～40分程度の短縮シフトに加え、長時間のリアルタイム観察も選択可能。

### 指令業務だけで飽きない仕組み

1. 平日・休日・昼夜・季節・天候で毎回異なる需要。
2. 計画・改善を主体とする通常勤務。重大な障害の頻発には頼らない。
3. イベント輸送、車両運用、予備編成、検修、ダイヤ改正、乗務員配置。
4. 指令員としての専門技能、経験、同僚の信頼、役割と権限の変化。
5. 新人から熟練指令、班長、指令長、専門職継続などのキャリア分岐。
6. 他部署のAI担当者との連絡、相談、業務調整、引継ぎ。
7. 将来の混雑、車両更新、基地増強の影響を業務上の見通しとして扱う。
8. プレイヤー自作の運行課題・勤務シナリオ、プレイ記録の比較。
9. 重大な選択が人物関係や章の展開を変える物語。
10. 物語終了後の長期継続勤務。年単位で地域・列車・設備・人員が変化。

安全性だけでなく、旅客への影響、正確な判断、情報共有、長期改善を評価し、理由を明示する。

# 第10A章｜R7「配属先は、明日変わる」— 超リアル社員異動・長編キャリア【v3.2新規】

## 10A.1 独立性と設計思想

**「新入社員から会長へ」R5とは別の、現実の社員生活を掘り下げた独立モード。** R5が長期の昇進と世代交代を描く一方、R7は**配属・希望・異動・研修・勤務・専門性・同僚・通勤・暮らし・迷い・再挑戦**を中心に描く。社長・会長になる必要はなく、専門職として定年まで勤めることや他地域で働くことも対等に価値あるエンディングとする。経営・予算編成・人事管理UIを強制せず、主人公は**社員として自分の業務を遂行する**。

## 10A.2 社員生活モデル

- **雇用と所属**：新卒／中途相当の入社経路、系統・職種、勤務地、事業所、所属班、責任範囲、勤続年数、在籍部署。
- **勤務のリアリティ**：交替勤務、日勤、早番・遅番、休憩、当直・宿直が適合する職種、連続勤務を避ける条件、休日、有給休暇、研修日、出張、引継ぎ、繁閑の差。
- **異動の判断**：希望申告、面談、所属先の必要人数、本人の適性、保有資格、実績、育成方針、勤務地事情、受入部署の教育余力。結果は必ずしも希望どおりにならない。
- **異動の種類**：同系統内の異動、拠点異動、専門職継続、本人希望による応募、公募制度、期限付きプロジェクト、関連部門への出向（架空制度）。専門系統の横断には採用区分・研修・適性・資格の壁を設ける。
- **仕事の修得**：新部署で無資格なのに即日運転・設備操作できるようにしない。資格要件、現場の監督、教育課程、見習い期間、理解度テスト、訓練成果をゲーム化する。
- **人間関係の継続**：旧部署の先輩・同僚と関係が続き、数年後の再会・異動先の評判・過去の引継ぎ品質に影響する。
- **生活の変化**：移動時間、転居・単身赴任・家族行事などは選択制で配慮深く描く。過度に個人情報を扱わず、ゲーム内の架空プロフィールに限定する。
- **倫理と組織文化**：報連相、相互理解、改善提案、現場の知恵、配属希望と組織の必要性の葛藤。安全や労働法を無視することを成功条件にしない。

参考とする現実の制度はJR東海の職種・採用・配置FAQ、JR東日本の人事・キャリア紹介などの**公開情報**。実在企業固有の制度を「青嶺広域鉄道」の全社員に機械的に適用せず、**架空の人事規程と資格要件**を明文化する。

## 10A.5 重要分岐と結末

- 希望部署への応募、現部署での専門技能継続、異動の受諾・再検討、研修への投資、後輩育成、上司への説明、誰と協力するか。
- 人物の信頼だけでなく、技能・経歴・勤務実績・資格・転居可否が将来の選択肢を変化させる。
- エンディング例：駅の専門家、車両基地の熟練者、社内教育者、地域連携の中心人物、複数部署をつないだコーディネーター、地元勤務を選んだ人生、転職して新天地で活躍、再挑戦を続ける未来。**昇進しない結末を失敗と扱わない。**

# 第10B章｜R8「消えた引継ぎ帳」— 非暴力・職場調査サスペンス【v3.2新規】

## 10B.1 トーン

**ホラー、殺人、失踪事件、残虐描写、幽霊、怪異を一切用いない。** 緊張感は部署間に残る見解の食い違い、過去の決裁記録、引継ぎ文書の所在、人間関係、説明責任、期限の接近から生む。主人公は社内の改善プロジェクト担当であり、探偵のように法や規程を破る行為はしない。

## 10B.2 あらすじ

車両基地の設備更新プロジェクトで、旧版の引継ぎ帳に記載されていた重要な但し書きだけが現行の説明資料と一致しないことが判明する。最初は単なる転記の誤りと思われたが、数年前の議事録、現場担当者の記憶、関係部署の判断基準が次々と異なっていた。誰が悪いかを決めつけず、当時の事情と文書の変遷を丁寧に確認するうち、会社の意思決定そのものを問い直す必要が生じる。

## 10B.3 プレイ

- 3D車両基地・事務室・駅の探索、許可された関係者への聞き取り、資料照合。
- 2Dタイムライン、版管理された文書、関係者の主張、相関図、矛盾マーカー。
- 同じ資料の解釈が複数成立する場合、プレイヤーの推論を一つに固定しない。
- 証拠の未確認部分は未確認として扱い、根拠のない断定には業務上の信頼低下など合理的な影響を与える。

## 10B.4 長編8シーズン

1. 白紙の一頁／2. 初期の証言／3. 基地の記憶／4. 旧部署とのすれ違い／5. 資料の版と年月／6. 説明会前夜／7. 失われた合意の再構築／8. 引継ぎ帳の最後の頁。

それぞれ12章以上、**合計96章以上**。主要分岐は「誰に、どの時点で、どの根拠を示すか」。主要な真相・職場関係・改善の方向性に意味の異なる複数結末を設定する。

# 第10C章｜R9「特急42号の空白」— タイムライン・ヒューマンミステリー【v3.2新規】

## 10C.1 トーンと禁止事項

殺人・危害・ホラーではなく、**架空の運行記録と人間の記憶の食い違い**を扱う。鉄道保安装置の脆弱性、実在指令システムへの介入、運転妨害の詳細を描かない。列車は安全に運行され、謎の中心は記録の整合性、案内の時差、列車番号の扱い、旧ダイヤ資料の誤認などの非暴力的な問題である。

## 10C.2 あらすじ

廃止予定の地方駅に展示される「特急42号の運転史」には、複数の時代の時刻表、写真、車内広報資料に一致しない記述がある。元駅員と現役乗務員の記憶も違う。企画担当の主人公は地域記念展示の責任者となり、当時を知る人々の証言と文書を集める。謎を追ううちに、ある人物のキャリアと町の歴史の見え方が変わっていく。

## 10C.3 プレイ

- 年代別のダイヤ・時刻表・路線図を2Dで比較。
- 3Dの駅や車内で写真と現在位置を照合。
- 擬似3Dの回想再現を仮説ごとに並べ、確定情報と推定を区別。
- 誰を信じるかだけでなく、証言の限界や相手の事情を理解する。

## 10C.4 長編8シーズン

1. 記念展示の依頼／2. 42号の写真／3. 食い違う時刻表／4. 三人の元職員／5. 季節列車の記憶／6. 未公開だった手紙／7. 駅が迎える最終日／8. 正しい歴史の伝え方。

各12章以上、合計96章以上。結末は記録の再評価、地域展示の方向性、人物関係、主人公の未来により分岐する。**不穏なホラー表現に頼らない。**

# 第11章｜自動車：車種・物理・レース・2つのストーリー

### 車種

一般乗用車、コンパクト、スポーツセダン、スポーツクーペ、GTレーシングカー、フォーミュラ型車両など、最初に5～6車種の架空車両を制作。市街地の交通ルールに従ったドライブと、閉鎖されたサーキットレースは別に扱う。

### 物理

車重、重心、重量配分、慣性、エンジン／モーターのトルク、変速機、駆動方式、デフ、タイヤの縦横スリップ、荷重移動、サスペンション、ブレーキ、ABS/TCS/ESC、空力、路面・雨・温度、摩耗、損傷を個別計算。汎用剛体の見た目だけで実車物理と称さない。

### C1 レーサーストーリー「ゼロからのチェッカー」

新人からレース界へ。ライバル、メカニック、チーム代表、スポンサーと関係を築き、車両選択・走行結果・契約・チームの対立などが将来を分岐。自由走行、予選、決勝、タイムアタック、AI対戦、ピット、リプレイ、テレメトリーを提供。

### C2 チーム経営「薄氷のチャンピオン」

ドライバーを操作せず、チーム設立、契約、資金、人材、技術開発、車両セットアップ、タイヤ・燃料・ピット戦略、シーズン計画を楽しめる。AIドライバーのレースを3D観戦し、その結果を経営・物語へ反映する。長期継続プレイに対応。

### C3 自由ドライブ

車両・天候・時間・交通量・コース・レース条件を自由変更。車両カスタム、タイヤ・サスペンション・ギア比等の設定、技術3D分解、走行記録、写真、リプレイ、自作イベント、適切な合法競技環境でのレースを提供。

# 第12章｜リアル音響・人物・街の反応

### 鉄道の音

主電動機、インバーター、歯車、車輪とレール、曲線、分岐、制動、空気圧縮機、ドア、警笛、空調、走行風、橋梁、トンネル、車内放送、基地の設備音。速度だけでなく回転数、力行／制動状態、線路条件、車内外、距離に連動する。

### 車の音

エンジン、吸気、排気、過給、変速、タイヤ、ブレーキ、風切り、サスペンション、衝撃、道路と車内外の反射。実録できない場合は適正にライセンスされた素材・独自合成を使用し、実車録音と偽らない。

### 職場の音

指令室・基地・駅・ピットの環境音、機器、通信、会話、通知。重要な業務通知には視覚表示と字幕も用意。Web Audio API、状態依存サンプル、レイヤリング、3D定位、必要時AudioWorkletを用いる。iPhoneの音声開始制約を考慮する。

### キャラクター

NPCごとに担当業務、性格、技能、過去の判断の記憶、人間関係、役職、勤務履歴、生活上の事情、台詞条件を持たせる。AIの会話を完全に無制約のランダム生成にせず、物語の整合性を保つ。

# 第13章｜分岐・マルチエンディングエンジン

**参考にするのは『Detroit: Become Human』のような分岐の密度、過去の選択の後効き、章別フローチャートという設計思想であり、同作品のシナリオ・キャラ・台詞・アセットは流用しない。**

1. 1章に原則1～3個の重要な明示的選択肢。
2. 会話以外の運転成績、業務判断、記録、行動、時間切れ、誰と協力したかも分岐条件。
3. 一時的にルートが再合流しても、選択・人物関係・世界状態の履歴を保持。
4. 途中の選択で後の操作内容・使用可能な職種・同僚・台詞・章・結末を変える。
5. 主要ストーリー12本、**各8シーズン以上・計96章以上**を最終企画目標とする。R5の従来16章は骨子として保持し、96章以上の詳細場面へ展開する。
6. 各主要ストーリーに8種類以上の**意味の異なる**大きな結末を目標とする。重要人物別エピローグと組み合わせる。
7. 未到達分岐はネタバレを防ぎつつ章終了後に可視化できる。
8. ストーリーグラフ、条件評価、結果適用、履歴、セーブ、エンディング解決、フローチャートのモジュールを持つ。
9. 到達不能なノード、矛盾する選択、保存再開で変わる分岐をテストで検出。

**R5〜R11は経営シミュレーションを含めない。** R2のみ鉄道経営が主軸。R3のみ運行指令の専門業務が主軸。ストーリー間の同一人物カメオ出演は可能でも、ゲーム進行依存は持たせない。

# 第13A章｜既存作を含む12キャンペーンの超長編化【v3.2最優先】

## 13A.1 統一ボリューム基準

**対象12本：R1、R2、R3、R5、R6、R7、R8、R9、R10、R11、C1、C2。** 2つのフリープレイR4・C3にはストーリークリアを要求しない。

- **各作品8シーズン以上、1シーズン12章以上、合計96章以上**を最終制作目標とする。話数より内容の個別性・因果関係・実プレイの濃さを優先する。
- 1つの章は約25〜75分相当を目標に、導入／通常の仕事または自由行動／人物イベント／重要判断／余波を構成。全章が一律の長さである必要はない。
- **メインストーリー60〜120時間／本、分岐探索・後日談を含め100〜200時間級／本**は企画上の長期目標であり、すべてが自動生成で達成されるとは限らない。ゲームを動作させて実測する。
- 12作品合計で1,152章以上の計画規模。これは大規模商用ゲーム数本分に相当する。制作量、メモリ、配布容量、物語品質は**主要章の手作り、シミュレーションで変化する日常、アセット再利用、段階的検証**の組み合わせで成立させる。未制作章を完成済みに数えない。
- 最低8種類の**筋や人物の未来が実際に異なる主要エンディング／作品**を目標とする。単語差し替えだけの結末を数えない。
- 各シーズンに中心課題、職場・登場人物の変化、独自の操作、複数の分岐、回収する伏線を設ける。重要な選択を毎章無理に増やさず、物語のリズムに合わせる。
- 長編化のための反復お使い、長いだけの会話、同じ業務の数値水増し、無意味な移動を禁止する。途中離脱・再開しやすい章要約、履歴、時間軸、人物相関、伏線ノートを提供。

## 13A.2 既存ストーリー7本の8シーズン骨子

**R1「最後の定時」運転士**：①入社と運転準備 ②初乗務 ③担当線区の拡張 ④同期ライバルとの競争 ⑤季節と日常輸送の工夫 ⑥後輩を育てる ⑦会社・車両の世代交代 ⑧自分の運転を次世代に伝える。運転そのものの上達と安全・判断・仲間のドラマを中心にする。

**R2「消えゆく路線、残すべき未来」鉄道経営**：①状況把握 ②財務と需要 ③日常輸送の再設計 ④新車・設備更新 ⑤地域との調整 ⑥長期事業計画 ⑦事業環境の変動 ⑧数十年後の鉄道網。経営のみで完走可能。

**R3「運行の境界線」指令**：①研修・引継ぎ ②通常ダイヤ監視 ③専門担当の定着 ④運用計画の最適化 ⑤異なる意見の同僚との関係 ⑥広域輸送と大規模イベント ⑦指令職の世代交代 ⑧指令の未来。指令員として同じ職種で全章完走可能、障害ばかりではなく日常業務・計画改善が中心。

**R5「新入社員から会長へ」**：①入社 ②駅・車両基地研修 ③初期の専門職 ④部署間協力 ⑤中堅への成長 ⑥人材育成と会社の変化 ⑦次世代のリーダー ⑧会長に至る人生の回収。従来16章の節目案を章群へ展開。**主要な完走ルートは会長に就任する**が、価値ある専門職等の別ルートも用意。経営シミュレーションなし。

**R6「交差するレール」群像劇**：①各視点の出会い ②古い記録 ③駅・車両基地の交差 ④人物ごとの違う証言 ⑤仕事と地域の過去 ⑥協力か距離か ⑦複数の真相の照合 ⑧再会と新しい日常。**ホラー・殺人のない群像ミステリー**に限定。

**C1「ゼロからのチェッカー」レーサー**：①初めての競技 ②車両調整 ③ライバルとの出会い ④チームへの加入 ⑤成績と不調 ⑥大型シリーズ ⑦選択したチームと関係者の未来 ⑧競技人生の決着。長いレース日程・練習・チーム内ドラマと分岐。

**C2「薄氷のチャンピオン」チーム経営**：①チーム創設 ②予算とスポンサー ③ドライバー育成 ④車両開発 ⑤厳しいシーズン ⑥スタッフとチーム文化 ⑦大規模な体制刷新 ⑧次世代へ続くチーム。**ドライバー操作なし**で完走可能。

R7〜R11の各8シーズンは第10A〜10E章に定義したとおりとする。これらも同じ長編品質基準に従う。

## 13A.3 大河ドラマとしての年月経過

- 長期物語に年表・イベント時系列・年齢・入社年度・異動履歴・役職・資格・駅／車両／設備更新の履歴を持つ。
- 同一人物が若手からベテランへ変化し、容姿・声の表情・話し方・人間関係・生活を変える。職種別制服と名札の変更も3D／2.5Dで再現する。
- 同じ駅や基地は年月により設備が変わるが、その変化に設定上の理由を持たせる。数年を飛ばす場合は、年表で経過を追える。
- 過去の選択の影響が10〜30年後に発生しても、因果関係と説明可能性を維持する。時間の飛躍で人間関係や専門技能を初期化しない。
- R5の会長昇進は必然としない。**学習・推薦・社会人経験・採用制度・取締役選任などの架空会社内の制度に沿う**条件を設計し、物語上の到達を描く。会長になっても経営操作は必須にしない。
- 同一作品内の時系列、登場人物の年齢、部署、駅の改築、車両の運用年代が矛盾する場合は監査FAILとする。

## 13A.4 多重分岐の密度と実現手法

- 『Detroit: Become Human』のような**過去の選択の長期影響と章別フローチャートの考え方**を参考にするが、物語、台詞、人物、演出、UIの固有意匠はオリジナルにする。
- ノード数の指数爆発を避けるため、主要筋の分岐＋再合流後の状態依存＋人物・部署・技能のパラメータ変化を組み合わせる。再合流でも過去の選択を無効化しない。
- 重要分岐はすべて到達性テスト、過去因果テスト、セーブ再開テスト、表現整合性チェックを行う。
- 謎の真相は**証拠の確度**と区別し、誤解が解ける過程を描く。ロックされた資料の不正取得や実在インフラへの介入方法をプレイ目標にしない。
- ゲームは長期的な作者主導の筋を持ちつつ、通勤、勤務、日常イベント、天候、旅客、レース結果などシミュレーション変数によって中間シーンを変化させる。

モジュール例：

```text
  rendering/        # Three.js 3D、2.5D、2D、適応LOD、カメラ
  audio/            # 車両音、職場音、環境音
  ui/               # 操作、ダイヤグラム、指令、経営、字幕
  assets/           # バージョン付きマニフェスト
  platform/         # Artifacts、Vercel、ストレージ、配布差異

  tests/            # 単体、統合、E2E、性能、シナリオ検証
```

固定時間刻みで物理を計算し、描画FPSと分離する。描画表現・画面切替によって内部シミュレーションが変わらないこと。計算モデルが重い場合は段階的な数値精度・更新頻度を実測で調整し、視界外でも必要な運行結果を継続管理する。

iPhone Safariは30fpsを基本目標、対応する高性能端末では60fpsを目指す。FPS、フレーム時間、メモリ、発熱、電池、クラッシュ、音声起動、画面回転、タッチ誤操作、バックグラウンド復帰を実機で確認する。計測できない環境では未検証と記録する。

# 第17章｜視覚・動作・音響・業務の徹底監査【最重要】

**モデルを生成しただけ、コードが存在するだけ、1枚の綺麗な画像が得られただけでは合格にしない。** 実際にレンダリング、操作、計測して証拠を残す。監査能力が利用できない場合は必ず「UNVERIFIED」とする。

## 17.1 3Dモデル多視点監査

各鉄道車両・自動車・主要施設について、正面、背面、左右側面、左右斜め、上面、下面、運転台／コックピット、車内、台車／足回り、主要機器拡大を撮影。参考写真・公開寸法と対応する画角・尺度で比較し、寸法、輪郭、車輪・ドア位置、床下、屋根機器、塗装、材質、ライト、表記、部品欠落を確認する。

## 17.2 車両基地・路線の監査

- 基地の配線略図と3D線路の接続関係を照合。
- 留置線の有効長、編成の収容能力、車両限界、構内の通過可能経路を確認。
- 主要基地を全景、真上、接写、構内進入、検修庫内、夜景で撮影。
- キロポスト・信号・標識・架線・分岐・トンネル・橋梁の配置を目視確認。
- 浮遊、地面貫通、線路不連続、車体・設備干渉、コリジョン誤りを検出。

## 17.3 最高・最低品質画像

各主要車両・環境・基地について最低限：

- **最高品質設定：代表画像2枚以上**（特徴がよく見える画角）
- **最低品質設定：代表画像2枚以上**（同じ場面・比較可能な画角）
- 可能なら並列比較、差分、オブジェクト数、ポリゴン数、メモリ、FPSを添える。
- 低品質でも消えてはいけない操作情報、重要設備、列車の識別性を確認する。

## 17.4 動作監査

列車加減速、ブレーキ、曲線、車体揺動、ドア、台車、パンタグラフ、基地入換、洗浄・点検アニメーション、自動車の荷重移動・旋回・制動・サスペンション、走行AIの挙動を短い動画または連続フレームで確認。物理ログとの一致を検証。

## 17.5 3D／2.5D／2D切替監査

同一シーン・同一時刻のスクリーンショットを3方式で取得。列車位置、編成、乗客、路線状態、基地の占有、天候、物語イベントに齟齬がないか検証。方式切替時のカメラ・UI・時間・音声の整合性、フリーズ、メモリリークを検査。

## 17.6 運行指令・経営UI監査

- 計画／実績ダイヤと3D列車位置が一致するか。
- 運用画面の編成が基地・本線に実在するか。
- 機器の状態、通知、ログ、乗務員、旅客の数値が統一されているか。
- ダッシュボードの計算根拠が明確か。
- iPhoneで文字が読め、タップでき、重要情報を見失わないか。
- PCでは複数パネル同時表示、iPhoneではタブ／ズーム／詳細パネルで同一情報へアクセスできるか。

## 17.7 音響監査

音源の聴取比較、速度・回転数・負荷・距離との対応、突然の音切れ、ループ接合、極端な音量差、通知音の可聴性、権利情報を検証。可能なら波形・スペクトログラムを出す。音源がない場合に「実録再現済み」と記載しない。

## 17.8 数値・ストーリー・回帰テスト

列車の加減速・制動距離、レースカーの加速・制動・旋回、車両基地の編成占有、ダイヤ整合性、経営収支、全ストーリー分岐・エンディング到達性、セーブ再開、モード独立性を自動検査する。新しい機能追加後は既存機能も回帰検査する。

## 17.9 合否

全チェック項目に `PASS / FAIL / UNVERIFIED` を付ける。FAILは修正して再検査。UNVERIFIEDは検証できない理由と必要な手段を明記。実機検査や画像比較ができない場合に合格と偽らない。

# 第17A章｜超長編社員ドラマと非暴力サスペンスの専門監査【v3.2新規】

**R7〜R11を含む12ストーリーすべてに適用する。**

1. **配属・資格監査**：職種・免許・研修・異動可能性・在籍年数の整合。未経験なのに即日特殊業務に従事する描写、希望すれば無条件異動できる描写はFAIL。
2. **勤務監査**：勤務カレンダー、休息、引継ぎ、休暇、出張、繁忙期が設定した架空会社規程と合致するか。違法な長時間労働を推奨しない。

4. **人物関係監査**：人事異動前後の旧同僚・ライバル・先輩との信頼や記憶が保存されているか。
5. **サスペンス監査**：R6・R8・R9・R10ではホラー、殺人、人体損傷、超常現象、暴力的脅迫に依存していないか。恐怖演出ではなく、文書・発言・制度・倫理の謎が本当に成立しているか。
6. **情報整合監査**：同じ証拠・記録・会話が前章と矛盾する場合、意図した伏線か制作ミスかを区別。伏線は後の章で合理的に回収する。
7. **実画面監査**：駅、事務室、基地、研修、会議、記録画面、相関図、年表を3D／擬似3D／2Dの適切な方式で表示し、スクリーンショットを残す。

9. **長編品質監査**：各章の独自の意味、業務または探索のプレイ要素、伏線、感情変化を台帳で管理。同一の会話・任務が繰り返されるだけならFAIL。
10. **分岐監査**：12作品のエンディング到達性、重大な選択の反映、前半の判断の後効き、分岐フローチャートと実際の進行の一致を自動チェック。
11. **iPhone監査**：長文資料は読みやすいフォントと拡大可能なビューア、手掛かり比較は2段階タップ、音声会話には字幕、縦横切替時に物語状態が維持されること。
12. **アセット品質監査**：各長編で再利用した駅・基地・人物・制服に年代違い・部署違いがないか。最高／最低画質2枚ずつ、重要場面、登場人物、画面を記録。

評価は `PASS / FAIL / UNVERIFIED`。完成済みを証明するスクリーンショット、イベントログ、シナリオID、実機試験を紐付ける。全96章を制作していなければ、未制作の章は未実装と記録する。
